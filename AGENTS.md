# AGENTS.md

## What this is

A Chrome **Manifest V3** extension (`win98-newtab/`) that replaces the new-tab page with a Windows 98-style desktop of the user's Chrome bookmarks. The **runtime** is a single classic script `win98-newtab/newtab.js` (already bundled, no modules) — Chrome never sees modules or TypeScript. The runtime is a **build artifact**: `npm run build` (esbuild, format `iife`) bundles `src/app.js` + `src/lib/*.ts` into it, so `newtab.html` stays a plain static page. Editing the artifact by hand is forbidden — change the sources in `src/` and rebuild.

Source layout:
- `src/app.js` — the UI shell / orchestrator: recreating the windows that were open before a reload, wiring the injected slots (`panelActions`/`shellActions`) and `init()`. Everything else lives in `src/ui/*`. JSDoc-typed, **loose** checking on purpose (unannotated code stays `any`; the value comes from the typedefs below, so annotate the model, not the DOM plumbing; `querySelector` results usually need `/** @type {HTMLElement} */ (…)` casts — cast syntax is `/** @type {T} */ (expr)`, never put a trailing comma inside the parenthesized expression).
- `src/ui/*.js` — the UI modules: `dom.js` (element refs/helpers), `icons.js` + `favicon.js` (icon generation/cache), `clock.js`, `storage.js`, `windows.js`, `dialogs.js`, `contextmenu.js`, `settings.js`, `settingsWindow.js`, `weather.js`, `calendarWindow.js`, `searchWindow.js`, `notepad.js`, `calculator.js`, `desktop.js`, `folder.js`, `dragdrop.js`, `nodeOps.js`, `allBookmarks.js`, `events.js` (all event wiring: desktop click/marquee, clock, start menu, taskbar, keyboard), `liveSync.js` (bookmark tree loading + live sync). They import each other and the shared singletons; two late-bound slot objects are assigned by `app.js` at startup to keep the import graph acyclic — `panelActions` (cascade/tile/taskbar properties) in `windows.js` and `shellActions` (render desktop / refresh folder windows / refresh weather) in `shellActions.js`.
- `src/state.js` — the `state` singleton (window/settings/tree state) plus `findNodeById(id)`; `src/constants.js` — named constants (`CLICK_DEBOUNCE_MS`, `MIN_WINDOW_*`, …).
- `src/types.d.ts` — the canonical JSDoc typedefs (`BookmarkNode`, `Settings`, `WallpaperSettings`, `WinData`, `IconEl`, `SearchUI`, `SearchNode`, `CalendarEvent`). Each `.js` module keeps local `/** @typedef {import("./types").X} X */` aliases.
- `src/lib/*.ts` — pure logic (theme, settings, bookmarks, search, format), **strict** TypeScript, no DOM/chrome.*, covered by vitest unit tests in `tests/`.

## Verify / run

- After any change: rebuild (`npm run build`), reload the extension at `chrome://extensions/` (Developer mode → Load unpacked → the `win98-newtab` folder), then open a new tab.
- **Type check** (dev-only): `npm run typecheck` runs BOTH passes — loose+JSDoc over `src/app.js` (tsconfig.json) and strict over `src/lib` + `tests` (tsconfig.lib.json). Keep it green after any edit. `tsc` never runs in the extension. **Caveat**: the loose pass has `noImplicitAny: false`, so a name that exists only as an assignment target (`panelActions.x = …`) or that is `null` in `strictNullChecks: false` code is **not** reported — a missing `import` in a UI module compiles clean and then throws `X is not defined` at runtime. Use the smoke test below to catch those.
- **Unit tests** (pure logic only): `npm test` (vitest). Node-side, no Chrome mocks needed — that's why lib modules avoid `chrome.*`/DOM.
- **Everything at once**: `npm run verify` (typecheck + test + build + `node --check`).
- Validate JSON with `ConvertFrom-Json` / `JSON.parse`.
- The extension only runs inside the new-tab context; testing navigation/opening behaviors requires bookmark permission to be granted.
- **DOM/behavior emulators** (dev-only, NOT committed): unit tests cover pure lib logic only, so behavior that needs DOM + `chrome.*` (window stack/cascade/tile, tray weather, calendar grid, search) is verified by driving the REAL new-tab page headless. The set lives in `%TEMP%\opencode\`: `weather-check.cjs` (weather provider fallback + details window), `calendar-check.cjs` (grid/holidays/events), `theme-check.cjs` (theme apply/reset), `ctx-debug.cjs`, plus `desktop-drag-check.cjs` (STALE — the free desktop dragging feature was rolled back; the latter only makes sense if it returns). Pattern: launch system Chrome (puppeteer-core, path `C:\Program Files\Google\Chrome\Application\chrome.exe`), **setViewport first** (the 800×600 default breaks screen-coordinate math), intercept `api.open-meteo.com`/`geocoding-api.open-meteo.com`/`api.met.no` with `request.respond({ headers: { "Access-Control-Allow-Origin": "*" } })` (the page fetches with `mode:"cors"` — a missing CORS header silently fails download; the page is loaded from `file://`, so CORS applies even though the real extension gets it from `host_permissions`), mock `chrome.bookmarks`/`chrome.storage` via `page.evaluateOnNewDocument` (back the stores with `window.localStorage` so they survive `page.reload()`), and assert real selectors (`.weather-icon`/`.weather-temp`, `.weather-stat-row`, `.cal-title`/`.cal-grid`/`.cal-cell`, `#clock`). **Watch out**: the editor's autocorrect injects junk tokens into written `.cjs` files (`HTMLift`, `true2016`, `settle(`) — always `node --check` + inspect after writing an emulator, fix the token garbage by hand before running; and puppeteer ≥25 silently ignores `clickCount` (use `{ count: 2 }` for `page.mouse.click`, otherwise a double-click never fires).
- **Runtime smoke test** (dev-only, NOT committed): `win98-smoke.cjs` in `%TEMP%\opencode\` drives the bundled `newtab.html` in headless Chrome with `chrome.*` mocked and the network intercepted, then asserts the whole window set boots: desktop icons + clock, start menu, settings (OK path → `shellActions`), notepad, calendar grid, tray weather + details window, folder window, all-bookmarks window, taskbar menu (`panelActions`) and search. Run it after any `src/ui` change — it is the only check that actually executes the modules and their import cycles.
- **Cache busting is automatic**: after bundling, `scripts/build.mjs` injects short SHA-256 hashes of `win98.css` and `newtab.js` into `newtab.html` as `?v=<hash>` query params. You never bump versions by hand — any runtime-affecting change gets a fresh hash on the next build (and both params only change when their own file changed). Commit the built `newtab.html` together with the bundle so the unpacked extension is self-contained.

## Type definitions (JSDoc, at the top of `src/app.js`)

- `BookmarkNode` = `import("./lib/bookmarks").BookmarkNode` (structural subset of `chrome.bookmarks.BookmarkTreeNode`; also covers the synthetic «Все закладки» node).
- `Settings` / `WallpaperSettings` — `import("./lib/settings")`; `mergeSettings()` returns `Settings`, `DEFAULT_SETTINGS` is typed `Settings`.
- `WinData` = `import("./lib/windows").ManagedWindow & {…app fields}` — one open window as the app sees it: the WindowManager's layout/lifecycle fields (id/x/y/w/h/dialog/minimized/maximized/prevBounds/zIndex) PLUS app-only expandos (`title`, `icon`, `winType`, `bookmarkId`, `el`, `currentNode`, `navStack`, `searchFilter`, `okButton`, `_savedIndex`). App fields are optional in the typedef purely so a plain `ManagedWindow` is assignable — every record in `state.windows` has them by the time app code reads it. Cast `windowManager.get(id)`/`open()` results to `WinData` before touching app fields. `okButton` is set by `openDialog` on the FIRST dialog button and used by `openPromptDialog`'s Enter handler.
- `IconEl` = `HTMLDivElement` — desktop icons and folder items; the bookmark node is NOT stored on the element, it lives in the `iconNodes` module's `WeakMap` (`setNodeForIcon`/`getNodeForIcon`; cast `closest(".desktop-icon")` results to it and call `getNodeForIcon(div)`).
- `SearchUI` = search-window wrap div with `filter`/`input` expandos; `SearchNode` = `import("./lib/search")` — index entry with `_tl`/`_ul`/`_pl`/`isFolder`/`path`.
- `state` fields are annotated inline (windows/settings/treeRoot/searchNodes/nodeIndex/selectedDesktopEl). `nodeIndex` is a **Map** (`Map<string, BookmarkNode>`), not an object.
- `eventTargetElement(e)` — helper for the `e.target.closest(...)` pattern (TS types `EventTarget` without `closest`); use it for new listeners instead of reaching for `e.target.closest` directly.

## Facts about src/lib (pure, unit-tested in tests/)

- `format.ts` — `escapeHtml`, `clampInt` (range clamp; `null` for non-finite), `formatDateTime(ts)` (ru-RU «13 сентября 2026 г., 14:05»; `toLocaleString` doesn't throw on garbage — returns «Invalid Date», same as the original in-app code).
- `bookmarks.ts` - `BookmarkNode` interface, `ROOT_ORDER`/`ALL_ROOT_ID`, predicates (`isFolderNode`/`isBookmarkNode`/`isVisibleNode`/`isRootFolder`), `buildNodeIndex`, `getNodePath(node, nodeIndex)` - note the second args: callers in `src/ui/*` pass `state.nodeIndex`. Also `buildAllBookmarksNode(tree)` — the synthetic «Все закладки» root, rebuilt fresh on every call (never cached), children filtered through `isVisibleNode`. Also `FOLDER_COLORS` palette, `folderColorFor(id)` (deterministic string-hash tinting so a folder keeps its color across refreshes), `folderColorAt(i)` (cycle palette by index).
- `theme.ts` — `THEME_OPTIONS`, `THEME_COLORS`, `CUSTOM_THEME_KEYS`, `shadeColor`, and the palettes resolver `themeColorsFor(themeId, customColors)` + reset set `themeResetKeys()`.
- `settings.ts` — `Settings` shape, `DEFAULT_SETTINGS`, choice lists (`ICON_SIZES`/`FOLDER_STYLES`/`UI_FONTS` — also used by the settings form) and the whitelist `mergeSettings()`.
- `weather.ts` — pure weather client logic (no fetch/DOM/chrome.*), **two providers**: Open-Meteo — `weatherIcon(code)` (WMO→emoji, e.g. 2→⛅), `windDirName(deg)` (rus compass, 0→С, 90→В), `buildGeocodingUrl(city)`, `buildForecastUrl(lat, lon)`, `firstGeocodeHit(json)` (first hit → {latitude,longitude}), `parseWeatherCurrent(current, city, updated)` (normalizes the API `current` block into a `WeatherData`-like record: `temp/feelsLike/humidity/precipitation/windSpeed/windDirName/cloudCover/code/updated`); and met.no/Yr — `buildYrForecastUrl(lat, lon)` (`/weatherapi/locationforecast/2.0/compact`), `parseYrCurrent(payload, city, updated)` (reads `properties.timeseries[0].data.instant.details`, wind m/s → km/h, labels the update time from `properties.meta.updated_at`), `weatherCodeFromConditions(cloudCover, precipitation, tempC)` (met.no has no WMO code → derived), `apparentTemperature(tempC, humidity, windKmh)` (NWS felt temperature: wind chill / heat index / comfort). Plus `WEATHER_PROVIDERS: WeatherProviderId[]` (`["open-meteo", "yr"]`) - consumed by the fallback chain in `src/ui/weather.js`. `formatUpdatedTime`. NOTE: Open-Meteo geocoding returns `results[0].name`, but the page prefers the *stored* `weatherCity`. Used by the tray weather, the weather details window, and the weather window (`.weather-icon`/`.weather-temp` in tray `#weather`).
- `calendar.ts` — pure month-grid math (no DOM): `MONTHS` (ru long «январь»…«декабрь»), `monthTitle(year, month)` (`«сентябрь 2026 г.»`), `formatDayTitle(year, month, day)` (`«воскресенье, 13 сентября 2026 г.»`), `addMonths(year, month, delta)` (wraps across the year), `monthCells(year, month)` (Monday-first grid: leading `null` cells then 1..days, e.g. 2024-02 → 32 cells, 29 days), `todayInMonth(year, month)` (`1..31` | `null`).
- `holidays.ts` — pure Russian day-status logic (no DOM/chrome.*): `RU_FIXED_HOLIDAYS` (14 federal days per ст.112 ТК), `RU_YEAR_TRANSFERS` (verified per-year anomaly tables for 2024–2026: extra off days + forced working Saturdays), `ruDayInfo(year, month, day, transfers?)` → `{ isDayOff, status: "holiday"|"dayoff"|"work"|"weekend", holidayName }` following a cascade: registered transfer → official named holiday → weekend (Sat/Sun) → workday; `nextWorkingDayAfter`, `monthDayStr`, `parseIsdayoffStatus(raw, year)` (converts an isdayoff.ru status string into a `RuYearTransfers` or `null` when the payload is all-zero / not yet published). Holidays that fall on a weekend roll to the next working day (skipping other holidays/weekends) unless explicitly overridden by a transfer.
- `calendarEvents.ts` — pure user-event model (no DOM/chrome.*): `CalendarEvent` (`id`, `title`, inclusive `startDate`/`endDate` "YYYY-MM-DD", `allDay`, `startTime`/`endTime` "HH:MM", `note`), `normalizeEvent` (trim + validate; garbage → `null`), `parseDateStr`/`toDateStr`, `normalizeTime` (`^(\d{1,2}):(\d{2})$` — accepts "9:05", clamps to 23:59), `eventCoversDay`, `eventsInMonth`, `eventsOnDay`, `compareEvents`/`sortEvents` (all-day before timed, then by time, then title), `formatEventTime` (`"весь день"` / `"09:00"` / `"09:00–11:30"` / `"—"`), `formatEventRange`, `formatDateStr`, `formatInputDate`/`formatInputTime`, `eventColorIndex`, `makeEventId`. The calendar window fetches RU holidays live from `isdayoff.ru/api/getdata?year=Y&country=ru` (one char per day: 0=work, 1=day-off, 2=holiday, 4=short pre-holiday; data for future years may be all-zero → falls back to the built-in rule); raw strings are cached in `chrome.storage.local` under `"isdayoffRaw"` (map year→string, persisted only when parsed non-null) and events live under key `"calendarEvents"` in `chrome.storage.sync` (user data — same sync-first pattern as settings, with `chrome.storage.local` as legacy/migration source and overflow fallback).
- `search.ts` — `SearchNode`, `buildSearchIndex(tree)` (flattens to searchable nodes with lowercased `_tl`/`_ul`/`_pl`), `scoreNode`, `filterSearchNodes(nodes, filter, limit)` (ranking + trim; only the *filters* take a `filter`/`limit`, so `test`/`t`/... are stable). Used by the search window's live filter.
- `calc.ts` — `evalOp(a, b, op)` — the calculator's binary arithmetic (`+ - * /`), `null` for division by zero or unknown ops.
- `iconNodes.ts` — `setNodeForIcon(el, node)` / `getNodeForIcon(el)`; a `WeakMap<Element, BookmarkNode>` that keeps the bookmark node off the DOM element (no expandos). Desktop icons (`createDesktopIcon` in src/ui/desktop.js) and folder items (`createFolderItem` in src/ui/folder.js) are registered here; delegated handlers, marquee selection and keyboard navigation read back via `getNodeForIcon`. Callers cast `closest(...)` results to `IconEl` first.
- `windows.ts` — pure window management, no DOM/chrome.*: `WindowManager` owns the lifecycle, z-order and focus of every open window. `open({width?, height?, dialog?, x?, y?, viewportWidth, viewportHeight})` returns a `ManagedWindow` (`id`, `x`, `y`, `w`, `h`, `dialog`, `minimized`, `maximized`, `prevBounds`, `zIndex`); `get(id)`, `focus(id)` (no-op when already active), `minimize(id)` (dialogs never minimize; focus falls back to the last visible window), `restore(id)`, `toggleMaximize(id)` (round-trips via `prevBounds`), `close(id)`, `cascade(w,h)` / `tile(w,h)` (windows fill the viewport minus `TASKBAR_HEIGHT = 28`). Pure geometry helpers: `computeWindowStackPosition({width, height, viewportWidth, viewportHeight, stackIndex, x?, y?})` centers new windows and nudges them down-right by `WINDOW_STACK_OFFSET = 28` px, wrapping after `WINDOW_STACK_WRAP = 6` windows; honors explicit `x`/`y` and clamps to the viewport. Cascade constants: `CASCADE_START = 28`, `CASCADE_STEP = 24`, `CASCADE_MAX_W = 420`, `CASCADE_MAX_H = 320`. The manager is the **sole writer** of layout/lifecycle state — `createWindow` in `src/ui/windows.js` calls `open()` and then decorates the returned record with app fields (`title`, `icon`, `winType`, `bookmarkId`, `el`, …). `state.windows` IS `windowManager.windows` (the app views it as `WinData[]`); the app must never push/remove into that array directly. App-side DOM sync (zIndex, `.inactive` titlebars, active taskbar button) lives in `syncActiveWindowVisuals()` in `src/ui/windows.js` — call it after any focus/minimize/restore/close; `bringToFront` is `windowManager.focus(id)` + sync.

When moving more logic out of `app.js` into `src/lib`, keep it free of `chrome.*`/DOM and add tests in `tests/`; the strict pass (tsconfig.lib.json) will enforce it.

## Non-obvious architecture facts

- **Bookmark root grouping**: Chrome root folder IDs are fixed regardless of UI language — `1`=Панель закладок (Bar), `2`=Другие (Other), `3`=Мобильные (Mobile). The app sorts by `ROOT_ORDER = {1,2,3}` (lib/bookmarks.ts) and inserts a full-width `.desktop-row-separator` between groups so each group starts on a new row. Any unknown/custom root is sorted to the end.
- **All folder + page + shortcut icons are generated at runtime on `<canvas>`** (`drawFolderIcon`, `drawPageIcon`) or fetched as Google favicons (`getFaviconUrl` → Google's undocumented `t1.gstatic.com/faviconV2` endpoint with `fallback_opts=TYPE,SIZE,URL`, which rasterizes the site's best favicon — including **SVG** and apple-touch-icon variants — into a PNG; 128px is always requested so vector originals downscale crisply). Bookmark icons are shown immediately from cache as the original favicon, then swapped to a background-cleaned copy via `faviconDataUrl(url, size)` (uses `fetch` + `createImageBitmap` + canvas; trims opaque near-white margins so icons with white/boxed source icons blend into the wallpaper; falls back to `drawPageIcon`). Only swap `img.src`; never restructure the icon element. **Cleaned favicons are cached persistently in `chrome.storage.local` under `"faviconCache"`** (keyed by the full favicon URL — size-independent since faviconV2 is asked for a fixed 128px, FIFO-capped at 800 entries, debounced save): every `setFaviconImage(img, url, size, fallbackSize)` hit renders from the in-memory cache (`cachedFavicon`) with zero network, and `ensureFavicon` dedupes in-flight fetches across desktop/folder-windows/search. A page **reload (F5/Ctrl+F5 — no API tells them apart) drops the cache** (`isPageReload` via `performance.getEntriesByType("navigation")[0].type === "reload"`, checked in `prepareFaviconCache` in the init chain before `loadBookmarks`), force-refreshing every icon from the network — this is the manual icon-refresh affordance. Icons are *not* re-fetched during incremental live-sync refreshes (`renderDesktopIcons` reuses `<img>` elements; `img.src` only changes when the node's URL changed). `drawFolderIcon(color, open, size, style)` supports three visual styles selectable via the `folderIconStyle` setting (`"classic"`, `"glossy"`, `"outlined"`); callers omit the 4th param and it reads the current setting automatically (`folderIconStyleName()`). The `"classic"` style is a **pixel-perfect copy of the original Win98 `shell32.dll` folder icons** (closed gold 48×48 256-color, open 32×32 with the blue sheet) — bitmap data lives in `FOLDER_BITMAPS` (`drawFolderBitmap` renders it centered with nearest-neighbor scaling, so it stays crisp at any size); `"glossy"`/`"outlined"` are procedural and still use the tint `color` param. Icon size is driven by the `--win98-icon-size` CSS variable **set on `document.documentElement` (`<html>`)**, not per-icon — so it cascades into opened folder windows and the «Все закладки» window too. Never hardcode icon px in markup; keep `currentIconSize()` / variable wiring. The same CSS-variable pattern also drives other desktop layout settings (label size `--win98-label-size`, icon gap `--win98-icon-gap`, desktop padding `--win98-desktop-pad-x/y`) — all applied together by `applyDesktopStyle()`.
- **Live sync**: the whole bookmark tree is cached in `state.treeRoot` (re-read on every `chrome.bookmarks` event — `onCreated/onRemoved/onChanged/onMoved`). `scheduleBookmarksRefresh()` debounces (250 ms) into `refreshAllBookmarks()`, which re-renders the desktop (`renderBookmarks`) and every open folder window whose `winData.bookmarkId` matches a node (`refreshOpenFolderWindows`). Folder windows are tagged with `bookmarkId` via `createWindow` opts; windows whose folder was deleted are closed automatically. **Desktop refresh is incremental** (`renderBookmarks(tree, force)` → `renderDesktopIcons(roots, force)`): existing icon elements are re-used and re-ordered via `replaceChildren` (no flicker, no favicon re-fetch, `.selected` state survives), so on a rename/creation/removal only the affected icons change. Pass `force=true` when every icon must be rebuilt (icon size / folder style settings changed — the OK/cancel/live-preview paths in the settings window do this). Folder tints are deterministic: `folderColorFor(id)` hashes the bookmark id instead of a positional counter, so a folder keeps its color across refreshes.
- **Folder-window navigation**: folder windows (and «Все закладки») are a single-window tree browser — opening a folder inside a window navigates **in place** via `navigateInWindow` (no new window). «Назад» walks the window's `navStack`, «Вверх» goes to the parent folder; Chrome root folders (`parentId === "0"`) go up to the synthetic «Все закладки» listing. `updateNavButtons()` disables «Назад» when `navStack` is empty and «Вверх» at the top level (no previous level). The toolbar also carries a view-mode toggle (Значки/Список, backed by the `folderViewMode` setting). The top «Все закладки» listing is a synthetic node `ALL_ROOT_ID = "__root__"` built by `buildAllBookmarksNode()`; `winType: "all-bookmarks"` marks the single-instance «Все закладки» window (single-instance checks live on `winType`, not title, since the title changes while browsing). `bookmarkId` always tracks the *currently displayed* folder so live sync refreshes the right content.
- **Separator nodes** (`url: ""`, no children) exist in the bookmarks tree and must never render — always filter with `isVisibleNode()` (`isFolderNode` = has `children` array AND no url; `isBookmarkNode` = has url).
- **Settings live in `chrome.storage.sync` under key `"settings"`** (user data - follows the user across devices via `syncStoredGet`/`syncStoredSet` in `src/ui/storage.js`, with `chrome.storage.local` as the legacy/fallback store: a value only present in local is lifted to sync on first read; a payload that exceeds the sync quota of 8 KB/item falls back to local so data is never lost). To add a setting, update ALL of: `DEFAULT_SETTINGS`, `mergeSettings()` (whitelist — unknown/old values are dropped, use `structuredClone` of defaults), and the settings-window UI in `buildSettingsForm()`. All three live in `src/lib/settings.ts`; the form builder stays in `src/ui/settingsWindow.js`. Stored keys must survive reloads. The settings window is **tabbed** (`.win98-tabs` / `.win98-tabpanel` in `buildSettingsForm`): tabs are «Обои», «Поведение», «Вид», «О системе» — new setting groups go into the fitting `tabPanels.<id>` panel (or add a new tab def + panel), and OK/Отмена buttons stay outside the panels so they are always visible. Bulk/rebuildable caches (faviconCache, isdayoffRaw, weather, window layout, notepad) intentionally stay in `chrome.storage.local`.
- **Single-instance windows** — the guard key matches the kind of window: fixed-title windows («Поиск», «Настройки») are found by `state.windows.find(w => w.title === ...)`; windows whose title changes while browsing use `winType` (`"all-bookmarks"`, `"calendar"`, `"weather"`). Windows are managed entirely in JS (`createWindow`/`bringToFront`/`closeWindow`), taskbar buttons and titlebar wiring are rebuilt per window.
- **Node operations** (open variants, copy, rename, delete, «Свойства»/`openProperties`) live in one place: `buildNodeContextMenuItems(node)` builds the right-click items for any bookmark/folder, reused by desktop icons, folder windows and search results. **Delete is permanent** (`chrome.bookmarks.removeTree`/`remove`) — there is no trash/recycle bin. Rename/delete/confirm prompt with Win98-style child dialogs; all bookmarks mutations go through the `chrome.bookmarks.*` API so live sync keeps the UI consistent. The desktop background has its own context menu (Обновить / Создать папку / Вставить / Открыть все закладки / Настройки) in the `$desktop` contextmenu handler; «Вставить» pastes `state.clipUrl`.
- **Dialogs** (`openDialog`) lay the scrollable `.win98-dialog` body and the `.win98-dialog-buttons` row out as **siblings** inside `.win98-window-content` (which gets `.win98-dialog-container`, a flex column). Buttons must stay outside the scrollable body or they scroll out of view — keep this layout for any new dialog. `openDialog` also stores the first button on **`winData.okButton`** (plus its own `body.okButton`); `openPromptDialog`'s Enter handler triggers `winData.okButton` — always reference the winData copy, a stale `body` reference breaks Enter-to-confirm.
- **Search window** flattens the cached tree with `buildSearchIndex()` into `state.searchNodes`; `Ctrl+F` and the «Поиск» start-menu item open it; results are re-filtered on `input` (ranked: title-starts-with > title-contains > url-starts-with > url-contains) and kept fresh by `refreshSearchWindow()` on bookmark events.
- **UI styles** are driven entirely by CSS variables in `:root` in `win98.css` — the classic Win98 palette (silver/white/black/dark-gray, `--win98-*`). Chrome colors that were hardcoded in CSS (`#e0e0e0` hover, `#e8e8e8` selection, radio borders, `#008080` preview) live in variables (`--win98-hover`, `--win98-inset-bg`, `--win98-wp-preview`, `--win98-radio-*`, `--win98-input-bg`). To change a color, add/edit a variable rather than hardcoding. The layout settings (icon size, label size, gap, desktop padding) are applied as CSS variables on `document.documentElement` by `applyDesktopStyle()`.
- **Appearance themes** (Настройки → Вид → Тема): the `theme` setting is `"classic"` (no overrides — CSS `:root` defaults) / `"olive"` / `"ocean"` / `"lavender"` / `"custom"`. `THEME_COLORS` maps each built-in theme to `--win98-*` variable overrides; `applyTheme()` (called from `applyDesktopStyle()`) resets and re-applies them on `document.documentElement`, deriving the reset set from `Object.values(THEME_COLORS)` + `CUSTOM_THEME_KEYS` — new theme keys are picked up automatically. Custom colors live in `settings.customColors` and are validated in `mergeSettings()` against `CUSTOM_THEME_KEYS` (hex only); title-bar gradients for custom mode are derived from the picked highlight/`--win98-navy` color via `shadeColor()`. `--win98-content-bg` (defaults to `--win98-white`) is the window content-area background — it stays independent so a theme can recolor the window interior while borders keep bright `--win98-white` highlights. Remember `--win98-white` itself is NOT themeable on purpose (it drives 3D lit edges, title/selected text, and input field backgrounds that pair with UA-black text — theming it would break light text on light inputs). The built-in set stays light: dark palettes clash with the non-themeable white 3D edges, scrollbars and calendar cells, so a dark theme (which would need `--win98-black` set to a light color) is intentionally not offered. Text on colored fills (start-menu sidebar, hovered menu descriptions) uses `--win98-white`, never `--win98-silver`. To add a themeable color, extend the theme keys + `THEME_COLORS` (the reset set in `applyTheme()` follows automatically).
- **Wallpaper by remote URL** uses `fetch(..., { mode: "cors" })` and is stored locally as a data URL; servers without CORS headers will fail to download — mention file upload as the fallback when this comes up.
- **Click mode** (single vs double) is handled in `createDesktopIcon`, `createFolderItem` (used by folder windows AND the «Все закладки» renderer — no third copy anymore) and the search results, with a ~350 ms debounce guard; all must stay in sync, driven by `isSingleClickMode()`. `createFolderItem(node, parentNode, options)` accepts an optional `options.navigateTo(folderNode)` — when present (inside folder windows / «Все закладки»), opening a folder navigates the same window instead of calling `openNode()` (which would open a new window).
- Permissions: `bookmarks`, `storage`, `unlimitedStorage` (the latter because wallpaper images **and the favicon cache** are stored as data URLs in local storage), plus `host_permissions` for `api.open-meteo.com` and `geocoding-api.open-meteo.com` (weather geocoding/forecast), `https://api.met.no/*` (the Yr/met.no forecast — the fallback provider), `https://*.gstatic.com/*` (favicon fetching — required for `faviconDataUrl`'s cross-origin `fetch` of the `faviconV2` endpoint), and `https://isdayoff.ru/*` (calendar holiday status). New network features must be added to `manifest.json`.
- **Weather provider fallback**: `api.open-meteo.com/v1/forecast` is unreachable from Russia (the TCP connect just hangs), so `refreshWeather` in `src/ui/weather.js` does NOT fetch it directly — `fetchForecastParsed(lat, lon, city)` walks `WEATHER_PROVIDERS` (`"open-meteo"` → `"yr"`, i.e. met.no) via `fetchJsonWithTimeout()` (AbortController, `WEATHER_FETCH_TIMEOUT_MS = 4000` per attempt) and returns the first provider that yields parsed data. The last working provider is remembered in `chrome.storage.local` under `"weatherProvider"` (`weatherProviderOrder`/`rememberWeatherProvider`) and moved to the front of the order, so a dead provider is only waited out once per session (~4 s), after which lookups are sub-second. Geocoding stays on Open-Meteo (`geocoding-api.open-meteo.com` still answers normally). On failure: a failed *geocode* hides the tray widget, but if every forecast provider fails the tray keeps the previously cached value. `chrome.storage.local.weather` still holds the rendered cache (`{city, ts, ...WeatherData}`).

## Conventions

- UI copy and this project are **Russian** — keep new labels/messages in Russian.
- Commit messages: conventional commits in English (`feat:`, `fix:`, `docs:`, `chore:`). Repo already has a git history on `master`.
- Styling must stay in the Win98 3D-border language defined in `win98.css` (outset/inset borders, `--win98-*` variables, silver/gray palette); new UI (dialog groups, radios, buttons) should reuse `.win98-groupbox`, `.win98-radio`, `.win98-btn`.
