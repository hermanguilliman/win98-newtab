# AGENTS.md

## What this is

A Chrome **Manifest V3** extension (`win98-newtab/`) that replaces the new-tab page with a Windows 98-style desktop of the user's Chrome bookmarks. The **runtime** is a single classic script `win98-newtab/newtab.js` (already bundled, no modules) — Chrome never sees modules or TypeScript. The runtime is a **build artifact**: `npm run build` (esbuild, format `iife`) bundles `src/app.js` + `src/lib/*.ts` into it, so `newtab.html` stays a plain static page. Editing the artifact by hand is forbidden — change the sources in `src/` and rebuild.

Source layout:
- `src/app.js` — the UI shell (DOM, windows, event wiring). JSDoc-typed, **loose** checking on purpose (unannotated code stays `any`; the value comes from the typedefs below, so annotate the model, not the DOM plumbing; `querySelector` results usually need `/** @type {HTMLElement} */ (…)` casts — cast syntax is `/** @type {T} */ (expr)`, never put a trailing comma inside the parenthesized expression).
- `src/lib/*.ts` — pure logic (theme, settings, bookmarks, search, format), **strict** TypeScript, no DOM/chrome.*, covered by vitest unit tests in `tests/`.

## Verify / run

- After any change: rebuild (`npm run build`), reload the extension at `chrome://extensions/` (Developer mode → Load unpacked → the `win98-newtab` folder), then open a new tab.
- **Type check** (dev-only): `npm run typecheck` runs BOTH passes — loose+JSDoc over `src/app.js` (tsconfig.json) and strict over `src/lib` + `tests` (tsconfig.lib.json). Keep it green after any edit. `tsc` never runs in the extension.
- **Unit tests** (pure logic only): `npm test` (vitest). Node-side, no Chrome mocks needed — that's why lib modules avoid `chrome.*`/DOM.
- **Everything at once**: `npm run verify` (typecheck + test + build + `node --check`).
- Validate JSON with `ConvertFrom-Json` / `JSON.parse`.
- The extension only runs inside the new-tab context; testing navigation/opening behaviors requires bookmark permission to be granted.
- **Cache busting is automatic**: after bundling, `scripts/build.mjs` injects short SHA-256 hashes of `win98.css` and `newtab.js` into `newtab.html` as `?v=<hash>` query params. You never bump versions by hand — any runtime-affecting change gets a fresh hash on the next build (and both params only change when their own file changed). Commit the built `newtab.html` together with the bundle so the unpacked extension is self-contained.

## Type definitions (JSDoc, at the top of `src/app.js`)

- `BookmarkNode` = `import("./lib/bookmarks").BookmarkNode` (structural subset of `chrome.bookmarks.BookmarkTreeNode`; also covers the synthetic «Все закладки» node).
- `Settings` / `WallpaperSettings` — `import("./lib/settings")`; `mergeSettings()` returns `Settings`, `DEFAULT_SETTINGS` is typed `Settings`.
- `WinData` — one open window; `el`, `currentNode`, `navStack`, `searchFilter`, `okButton` (`_savedIndex` etc.) are optional expandos. `okButton` is set by `openDialog` on the FIRST dialog button and used by `openPromptDialog`'s Enter handler.
- `IconEl` = `HTMLDivElement` — desktop icons and folder items; the bookmark node is NOT stored on the element, it lives in the `iconNodes` module's `WeakMap` (`setNodeForIcon`/`getNodeForIcon`; cast `closest(".desktop-icon")` results to it and call `getNodeForIcon(div)`).
- `SearchUI` = search-window wrap div with `filter`/`input` expandos; `SearchNode` = `import("./lib/search")` — index entry with `_tl`/`_ul`/`_pl`/`isFolder`/`path`.
- `state` fields are annotated inline (windows/settings/treeRoot/searchNodes/nodeIndex/selectedDesktopEl). `nodeIndex` is a **Map** (`Map<string, BookmarkNode>`), not an object.
- `eventTargetElement(e)` — helper for the `e.target.closest(...)` pattern (TS types `EventTarget` without `closest`); use it for new listeners instead of reaching for `e.target.closest` directly.

## Facts about src/lib (pure, unit-tested in tests/)

- `format.ts` — `escapeHtml`, `clampInt` (range clamp; `null` for non-finite).
- `bookmarks.ts` — `BookmarkNode` interface, `ROOT_ORDER`/`ALL_ROOT_ID`, predicates (`isFolderNode`/`isBookmarkNode`/`isVisibleNode`/`isRootFolder`), `buildNodeIndex`, `getNodePath(node, nodeIndex)` — note the second args: callers in `app.js` pass `state.nodeIndex`.
- `theme.ts` — `THEME_OPTIONS`, `THEME_COLORS`, `CUSTOM_THEME_KEYS`, `shadeColor`, and the palettes resolver `themeColorsFor(themeId, customColors)` + reset set `themeResetKeys()`.
- `settings.ts` — `Settings` shape, `DEFAULT_SETTINGS`, choice lists (`ICON_SIZES`/`FOLDER_STYLES`/`UI_FONTS` — also used by the settings form) and the whitelist `mergeSettings()`.
- `search.ts` — `SearchNode`, `buildSearchIndex(tree)`, `scoreNode`, `filterSearchNodes(nodes, filter, limit)` (ranking + trim; used by the search window's live filter).
- `iconNodes.ts` — `setNodeForIcon(el, node)` / `getNodeForIcon(el)`; a `WeakMap<Element, BookmarkNode>` that keeps the bookmark node off the DOM element (no expandos). Desktop icons (`createDesktopIcon`) and folder items (`createFolderItem`) are registered here; delegated handlers, marquee selection and keyboard navigation read back via `getNodeForIcon`. Callers cast `closest(...)` results to `IconEl` first.

When moving more logic out of `app.js` into `src/lib`, keep it free of `chrome.*`/DOM and add tests in `tests/`; the strict pass (tsconfig.lib.json) will enforce it.

## Non-obvious architecture facts

- **Bookmark root grouping**: Chrome root folder IDs are fixed regardless of UI language — `1`=Панель закладок (Bar), `2`=Другие (Other), `3`=Мобильные (Mobile). The app sorts by `ROOT_ORDER = {1,2,3}` (lib/bookmarks.ts) and inserts a full-width `.desktop-row-separator` between groups so each group starts on a new row. Any unknown/custom root is sorted to the end.
- **All folder + page + shortcut icons are generated at runtime on `<canvas>`** (`drawFolderIcon`, `drawPageIcon`) or fetched as Google favicons (`getFaviconUrl` → `https://www.google.com/s2/favicons?domain=...&sz=...`). Bookmark icons are shown immediately from cache as the original favicon, then swapped to a background-cleaned copy via `faviconDataUrl(url, size)` (uses `fetch` + `createImageBitmap` + canvas; trims opaque near-white margins so icons with white/boxed source icons blend into the wallpaper; falls back to `drawPageIcon`). Only swap `img.src`; never restructure the icon element. `drawFolderIcon(color, open, size, style)` supports three visual styles selectable via the `folderIconStyle` setting (`"classic"`, `"glossy"`, `"outlined"`); callers omit the 4th param and it reads the current setting automatically (`folderIconStyleName()`). The `"classic"` style is a **pixel-perfect copy of the original Win98 `shell32.dll` folder icons** (closed gold 48×48 256-color, open 32×32 with the blue sheet) — bitmap data lives in `FOLDER_BITMAPS` (`drawFolderBitmap` renders it centered with nearest-neighbor scaling, so it stays crisp at any size); `"glossy"`/`"outlined"` are procedural and still use the tint `color` param. Icon size is driven by the `--win98-icon-size` CSS variable **set on `document.documentElement` (`<html>`)**, not per-icon — so it cascades into opened folder windows and the «Все закладки» window too. Never hardcode icon px in markup; keep `currentIconSize()` / variable wiring. The same CSS-variable pattern also drives other desktop layout settings (label size `--win98-label-size`, icon gap `--win98-icon-gap`, desktop padding `--win98-desktop-pad-x/y`) — all applied together by `applyDesktopStyle()`.
- **Live sync**: the whole bookmark tree is cached in `state.treeRoot` (re-read on every `chrome.bookmarks` event — `onCreated/onRemoved/onChanged/onMoved`). `scheduleBookmarksRefresh()` debounces (250 ms) into `refreshAllBookmarks()`, which re-renders the desktop (`renderBookmarks`) and every open folder window whose `winData.bookmarkId` matches a node (`refreshOpenFolderWindows`). Folder windows are tagged with `bookmarkId` via `createWindow` opts; windows whose folder was deleted are closed automatically. **Desktop refresh is incremental** (`renderBookmarks(tree, force)` → `renderDesktopIcons(roots, force)`): existing icon elements are re-used and re-ordered via `replaceChildren` (no flicker, no favicon re-fetch, `.selected` state survives), so on a rename/creation/removal only the affected icons change. Pass `force=true` when every icon must be rebuilt (icon size / folder style settings changed — the OK/cancel/live-preview paths in the settings window do this). Folder tints are deterministic: `folderColorFor(id)` hashes the bookmark id instead of a positional counter, so a folder keeps its color across refreshes.
- **Folder-window navigation**: folder windows (and «Все закладки») are a single-window tree browser — opening a folder inside a window navigates **in place** via `navigateInWindow` (no new window). «Назад» walks the window's `navStack`, «Вверх» goes to the parent folder; Chrome root folders (`parentId === "0"`) go up to the synthetic «Все закладки» listing. `updateNavButtons()` disables «Назад» when `navStack` is empty and «Вверх» at the top level (no previous level). The toolbar also carries a view-mode toggle (Значки/Список, backed by the `folderViewMode` setting). The top «Все закладки» listing is a synthetic node `ALL_ROOT_ID = "__root__"` built by `buildAllBookmarksNode()`; `winType: "all-bookmarks"` marks the single-instance «Все закладки» window (single-instance checks live on `winType`, not title, since the title changes while browsing). `bookmarkId` always tracks the *currently displayed* folder so live sync refreshes the right content.
- **Separator nodes** (`url: ""`, no children) exist in the bookmarks tree and must never render — always filter with `isVisibleNode()` (`isFolderNode` = has `children` array AND no url; `isBookmarkNode` = has url).
- **Settings live in `chrome.storage.local` under key `"settings"`**. To add a setting, update ALL of: `DEFAULT_SETTINGS`, `mergeSettings()` (whitelist — unknown/old values are dropped, use `structuredClone` of defaults), and the settings-window UI in `buildSettingsForm()`. All three live in `src/lib/settings.ts`; the form builder stays in `src/app.js`. Stored keys must survive reloads. The settings window is **tabbed** (`.win98-tabs` / `.win98-tabpanel` in `buildSettingsForm`): tabs are «Обои», «Поведение», «Вид», «О системе» — new setting groups go into the fitting `tabPanels.<id>` panel (or add a new tab def + panel), and OK/Отмена buttons stay outside the panels so they are always visible.
- **Single-instance windows** — the guard key matches the kind of window: fixed-title windows («Поиск», «Настройки») are found by `state.windows.find(w => w.title === ...)`; windows whose title changes while browsing use `winType` (`"all-bookmarks"`, `"calendar"`, `"weather"`). Windows are managed entirely in JS (`createWindow`/`bringToFront`/`closeWindow`), taskbar buttons and titlebar wiring are rebuilt per window.
- **Node operations** (open variants, copy, rename, delete, «Свойства»/`openProperties`) live in one place: `buildNodeContextMenuItems(node)` builds the right-click items for any bookmark/folder, reused by desktop icons, folder windows and search results. **Delete is permanent** (`chrome.bookmarks.removeTree`/`remove`) — there is no trash/recycle bin. Rename/delete/confirm prompt with Win98-style child dialogs; all bookmarks mutations go through the `chrome.bookmarks.*` API so live sync keeps the UI consistent. The desktop background has its own context menu (Обновить / Создать папку / Вставить / Открыть все закладки / Настройки) in the `$desktop` contextmenu handler; «Вставить» pastes `state.clipUrl`.
- **Dialogs** (`openDialog`) lay the scrollable `.win98-dialog` body and the `.win98-dialog-buttons` row out as **siblings** inside `.win98-window-content` (which gets `.win98-dialog-container`, a flex column). Buttons must stay outside the scrollable body or they scroll out of view — keep this layout for any new dialog. `openDialog` also stores the first button on **`winData.okButton`** (plus its own `body.okButton`); `openPromptDialog`'s Enter handler triggers `winData.okButton` — always reference the winData copy, a stale `body` reference breaks Enter-to-confirm.
- **Search window** flattens the cached tree with `buildSearchIndex()` into `state.searchNodes`; `Ctrl+F` and the «Поиск» start-menu item open it; results are re-filtered on `input` (ranked: title-starts-with > title-contains > url-starts-with > url-contains) and kept fresh by `refreshSearchWindow()` on bookmark events.
- **UI styles** are driven entirely by CSS variables in `:root` in `win98.css` — the classic Win98 palette (silver/white/black/dark-gray, `--win98-*`). Chrome colors that were hardcoded in CSS (`#e0e0e0` hover, `#e8e8e8` selection, radio borders, `#008080` preview) live in variables (`--win98-hover`, `--win98-inset-bg`, `--win98-wp-preview`, `--win98-radio-*`, `--win98-input-bg`). To change a color, add/edit a variable rather than hardcoding. The layout settings (icon size, label size, gap, desktop padding) are applied as CSS variables on `document.documentElement` by `applyDesktopStyle()`.
- **Appearance themes** (Настройки → Вид → Тема): the `theme` setting is `"classic"` (no overrides — CSS `:root` defaults) / `"olive"` / `"high-contrast"` / `"dracula"` / `"custom"`. `THEME_COLORS` maps each built-in theme to `--win98-*` variable overrides; `applyTheme()` (called from `applyDesktopStyle()`) resets and re-applies them on `document.documentElement`, deriving the reset set from `Object.values(THEME_COLORS)` + `CUSTOM_THEME_KEYS` — new theme keys are picked up automatically. Custom colors live in `settings.customColors` and are validated in `mergeSettings()` against `CUSTOM_THEME_KEYS` (hex only); title-bar gradients for custom mode are derived from the picked highlight/`--win98-navy` color via `shadeColor()`. `--win98-content-bg` (defaults to `--win98-white`) is the window content-area background — it stays independent so High Contrast/dark themes can use black windows while borders keep bright `--win98-white` highlights. Remember `--win98-white` itself is NOT themeable on purpose (it drives 3D lit edges, title/selected text, and input field backgrounds that pair with UA-black text — theming it would break light text on light inputs); dark themes must instead set `--win98-black` to a light color. Text on colored fills (start-menu sidebar, hovered menu descriptions) uses `--win98-white`, never `--win98-silver`. To add a themeable color, extend the theme keys + `THEME_COLORS` (the reset set in `applyTheme()` follows automatically).
- **Wallpaper by remote URL** uses `fetch(..., { mode: "cors" })` and is stored locally as a data URL; servers without CORS headers will fail to download — mention file upload as the fallback when this comes up.
- **Click mode** (single vs double) is handled in `createDesktopIcon`, `createFolderItem` (used by folder windows AND the «Все закладки» renderer — no third copy anymore) and the search results, with a ~350 ms debounce guard; all must stay in sync, driven by `isSingleClickMode()`. `createFolderItem(node, parentNode, options)` accepts an optional `options.navigateTo(folderNode)` — when present (inside folder windows / «Все закладки»), opening a folder navigates the same window instead of calling `openNode()` (which would open a new window).
- Permissions: `bookmarks`, `storage`, `unlimitedStorage` (the latter because wallpaper images are stored as data URLs in local storage), plus `host_permissions` for `api.open-meteo.com` and `geocoding-api.open-meteo.com` (weather) and `https://www.google.com/*` (favicon fetching — required for `faviconDataUrl`'s cross-origin `fetch`). New network features must be added to `manifest.json`.

## Conventions

- UI copy and this project are **Russian** — keep new labels/messages in Russian.
- Commit messages: conventional commits in English (`feat:`, `fix:`, `docs:`, `chore:`). Repo already has a git history on `master`.
- Styling must stay in the Win98 3D-border language defined in `win98.css` (outset/inset borders, `--win98-*` variables, silver/gray palette); new UI (dialog groups, radios, buttons) should reuse `.win98-groupbox`, `.win98-radio`, `.win98-btn`.
